一、三份材料分别解释什么

Anthropic 提供 always-on 的基础架构分解：事件进入持久化收件箱，定时器产生到期事件，run 在 session 中工作，独立记忆维持连续性，权限允许暂停待批，发件箱负责结果送达。关键语义是按事件短暂运行、休眠和再次唤醒。文章没有给出可供审计的完整实现。

DeepSeek 提供单仓库 coding agent 的监督和执行应用。README 明确称其为研究原型、参考代码，公开版本与内部实现及设计文章不完全相同。它作为 bundle 挂到 DeepSeek Harness，底层模型循环、会话持久化、工具和子代理由 @deepseek-ai/dsh-* 依赖提供。

LobeHub 提供跨 Web、服务端、设备等宿主的产品平台。通用运行时本身有源码；主动工作又分为邮件、群聊、定时任务、任务完成回传和反馈学习等多条路径。分析时必须分别标明其状态存储和执行条件。

二、DeepSeek 的完整主链路

来源插件 → Trigger → Thread → 两条分支：
  A. Subscription 扇出到已有 Ticket，作为 Input 交给该 Ticket 的 worker；
  B. Thread.pending → Eval → gate → 主 Session 的路由/语义研判 → Decision。
accept → 不可变 Mandate + Ticket + 首个 Assignment + 订阅 + 可选 ACK。
Assignment → launch effect → DshExecutor → 独立目录 + 持久 worker Session。
worker report → Ticket/Assignment 状态 → 主 Session relay → 按用途限制的 reply → Outbox → Channel。

Router 补充（2026-11-14）：主 Session 使用 dsh-superagent-router preset，角色名为 orchestrator；orchestrator_route 提供 accept、attach、ignore、stop。Router 负责工作与输入归属，Engine 负责政策核验和原子状态变更，DshExecutor 负责执行。原型没有在 Pi、Codex 等异构引擎中自动选择的实现。已明确归属的后续消息可以直接交给 worker，超出范围时再 handback。源码证据和本产品的映射见 docs/adr/0003-request-routing-and-dispatch.md。

核心文件：src/core/{model,ports,engine,part,intake,evals,tickets,assignments,replies,stage}.ts。
组装入口：src/index.ts → src/app/runtime.ts。

1. 领域对象为什么这样分

Source 是外部事件流，负责原生身份、读取游标、接收范围和 Trigger 翻译。
Trigger 是不可变事件，稳定 ID 负责去重与审计；正文和 meta 被视作外部数据。
Thread 是 Eval 串行和批处理边界，一条 Thread 同时最多一个 Eval。
Correlation 只补充上下文，不负责路由；Subscription 才负责路由。
Mandate 记录 strength、policyVersion、basis、actor 和 scope，表达这份工作授权来自哪里。
Ticket 是授权工作单位，可以结束后恢复；Assignment 是一次执行绑定，可以被重试或重启替换。
Session 与目录不定义业务任务状态，Ticket 自己定义结束条件。

这能避免把聊天线程、任务、一次执行、授权和模型上下文混成一个对象。

2. 接入、批处理与接单

Intake.receive 在事务中按 Trigger.id 查重，保存触发和 disposition，维护 Thread 关联并扇出。
人类消息到达已有 Ticket 后，通常由 worker 判断是否属于原工作，不再同时制造一个新工单。
其他消息在主 Thread 排队。新消息在 Eval 运行时累积为下一批。
Evals.start 选择批次中授权强度最高的合格触发，记录授权依据，调用 Assessor.request。
显式请求由主 Session 路由；推断候选经规则研判才能自动接受。
observe 默认只记录 would_accept；auto 才允许符合启用规则的推断任务接单。
研判结构要求每个启用规则恰好一个判断，且要求实现意图、确定方向和证据；这些证据的语义真实性仍由模型判断。
重复 accept 会查到原 Decision/Ticket，避免再次创建任务。

相关实现：src/policy.ts；src/core/evals.ts；src/app/assessment.ts；prompts/admission.md。

3. 上下文与授权分离

Subscription 上的后续消息可来自不同参与者或 bot；它们作为上下文进入 Ticket，不自动扩大 Mandate。
worker 可以 handback 超出范围的消息；只有所有负责它的 Ticket 都交回后才重新进入 Eval。
只读上下文订阅不取得该消息的处理权，也不唤醒已结束 Ticket。
普通人类后续消息可在原 Mandate 下恢复已结束 Ticket；人类停止的 Ticket 不再恢复。
恢复前重新核验当前 Policy。活动 Ticket 遇到 Policy 变更收到 Input；不会一律立即终止。
这一行为是明确设计取舍：保留进行中工作的收尾能力，但即时撤权不覆盖所有正在运行的行为。

4. 事务与副作用是可靠性的中心

Engine 是领域聚合的统一写入口。核心命令同步执行，Repositories.atomic 包住状态变化。
生产 Store 使用 SQLite，WAL + synchronous=FULL，嵌套 SAVEPOINT，运行目录由 proper-lockfile 排他占用。
状态变更与 effect 行在同一个数据库事务中提交；网络调用在事务外执行。
Effects 按 (kind,key) 合并待办，seq 保序，generation 防止旧执行完成时删除更新后的 payload。
六类 effect：assessment、launch、delivery、relay、notice、reply。
有按类型并发上限、指数退避、Later 延迟但不计失败、停止时保留待办。
afterCommit 用于取消内存中的运行等即时动作；需要跨崩溃保留的动作进入 Effects。

相关实现：src/app/{store,effects,passes,runtime}.ts。
测试核对：tests/effects.spec.ts 中事务回滚、运行期间更新 payload、并发上限、重试和重启后的队列接续。

5. 启动与执行恢复

Runtime：锁目录 → 开 Store → 组装组件 → 注册管理接口 → Setup → 安装 Session/Executor hooks → 创建主 Session → 同步 Policy → 恢复 Assignment → 启动 passes/effects。
DshExecutor 在 await 前同步预留 worker slot，避免最后一个空位被并发 launch 重复占用。
人类 follow-up 可额外使用一个 slot，避免被新任务挤住。
每个 Ticket 一个 worker-<ticketId> Session 和独立目录。目录准备由可配置 prepare 命令完成，可以使用 git worktree；独立目录不是 OS 隔离。
准备命令失败不自动重试，避免把残留目录误当成准备成功；等待人工重试或输入。
worker 的模型/网络瞬时故障有限重试；blocked/failed 后自动 CI/bot 输入保持记录但不继续唤醒。
后台 shell job 和子代理影响 slot 生命周期；向人交接后另有释放与收集结果规则。

重启时忙碌 Assignment 会被替换，并提示检查 worktree、git 历史和 GitHub 状态；已稳定 waiting/ready/blocked/failed 的执行可保留。
AgentDelivery 用稳定 message ID 检查会话历史与 pending inbox；发送后等待 sessionPersistence.flush。
Input 区分“已投递”与“已进入会话历史”。被取消的 step 只领取、尚未入历史的消息仍可重投。
Ticket 结束时，未读且未被确认处理的后续请求重新回到 Eval，避免默默丢失。

相关实现：src/executor/{dsh,background}.ts；src/app/{sessions,delivery}.ts；src/core/{assignments,tickets}.ts。
测试核对：tests/runtime-concurrency.spec.ts 的 what a worker read，特别是已投递但未读、进程内重启和崩溃遗留 inbox 的重投场景。

6. 结果发送与完成判断

Outbox 在事务中写 receipt 与 reply effect，保存 pending/sent/dropped 状态。
源关闭时保留消息等待；确定目的地失效或不再监听时标记 dropped。
同一 Ticket、同一会话的较晚消息等待较早消息，早一条反复失败后允许后续推进。
GitHub 使用隐藏 comment marker 查询已发送消息；飞书使用 idempotency key。
Reply 区分 acknowledgement、answer、result、attention，并由代码检查可发送用途与当前状态。
worker 的 progress 留在内部；结构化问题立即交给主 Session；主 Session 负责最终人类消息。
ready 对无 PR 工作可完成 Ticket；绑定 PR 的 Ticket 还要等待相关 PR 关闭/合并及未完 follow-up 收尾。

相关实现：src/core/replies.ts；src/app/outbox.ts；src/sources/{github-channel,feishu-channel}.ts。

7. 真实边界

ensure 把受管 Session 设为 danger-full-access。工具名单和 Ticket 结束检查由代码限制；授权范围的语义、禁止越界改动、许多合并条件仍依赖模型遵守指令。
命令 wrapper 默认选择 agent 账号，清理个人 token 与 git 环境；绝对路径程序可以绕过 PATH wrapper。项目文档也明确说明其不构成安全边界。
没有在此公开应用层找到文章式的通用定时任务/自主 follow-up timer API。现有周期工作主要为来源轮询、到期 Eval 检查、重试和健康检查；外部 DSH schedule 属于宿主能力。
没有找到独立的通用语义记忆提取/整理模块。持久领域状态、会话、文件和团队 skills 提供连续性；src/core/memory.ts 是测试用内存数据库，不是长期记忆系统。
数据库历史没有通用清理机制，Trigger、Decision、结束 Ticket、receipt 和版本历史会增长。
副作用队列与消息去重不能自动使任意 shell/API 操作 exactly-once。重启后外部操作的重复执行仍需查询外部状态与工具端幂等配合。

三、LobeHub 的运行时与主动工作链路

1. 通用 agent 运行内核

GeneralChatAgent.runner(context,state) 根据 phase 输出 instruction。
AgentRuntime.step 克隆状态、递增计数、取得 instructions、按序调用 executor、累计事件和使用量，返回 newState 与 nextContext。
指令包括 call_llm、call_tool、call_tools_batch、compress_context、request_human_approve、finish 等。
runAgentLoop 只负责继续条件和下一步 context；每个宿主提供 step，分别承担持久化、锁、流式通知与配额。
Host.transports 抽象 llm、messages、tools、stream、context、compression、subAgent 等能力。
executor 优先级允许 Agent 或宿主替换内置执行器。判断默认 fallback 行为时必须追到实际注入的 registry。

相关实现：packages/agent-runtime/src/{agents/GeneralChatAgent.ts,core/runtime.ts,loop/index.ts,executors/registry.ts,transport/host.ts}。

2. 工具执行、并发与人工暂停

GeneralChatAgent 检查工具 allow-list、空参数、全局审计、manifest 中的静态/动态 intervention 配置和用户模式。
always 级干预不会被 headless/auto-run 普通放行覆盖。headless 遇到必须干预的工具会生成 blocked tool result，让模型继续处理可做的部分。
request_human_approve 写入 durable tool rows、所属 assistant、batchId、operationId 和 stepIndex，并把状态置 waiting_for_human。
等待人工会结束旧 operation 的流；人工继续会创建新的 operation。异步工具等待通常继续同一 operation，两种等待不能混用。
异步工具在同轮还有待审批工具时，runtime 保存 deferredHumanApproval，恢复后再发出审批请求。
批量工具根据 ordered 和 serializeBy 分 lane：同一资源串行，不同 lane 可并行。
重投工具调用先检查已有 tool result；已持久结果可重放，避免直接重新执行。结果尚未持久化时，外部副作用仍需自己的幂等机制。

相关实现：packages/agent-runtime/src/executors/{tool,toolReplay,humanApprove}.ts。

3. 服务端每一步怎样可靠推进

executeStep：抢 operation 锁 → 读运行状态 → 处理 deferred init/取消/旧 step → 从 DB 取消息 → 前置 hooks → 组装 runtime → 执行一步 → 保存与发布 → 后置 hooks/trace → 续跑或完成。
AgentStateManager 将运行状态存在 Redis；普通状态 TTL 为两小时，刷新随保存发生。消息通常从状态快照剥离，规范消息在 PostgreSQL，下一步重新装载。
工具集另存，减少每一步反复序列化工具 schema；临时且无法从数据库重建的消息有保留例外。
下一步可交给队列，也可当前请求 inline 执行。inline 前先保存恢复 envelope；保存失败时退回队列。
锁有 owner、续租和有条件释放；对会重投的队列路径，提交前再次检查 ownership。
源码明确说明 ownership 检查和保存仍有间隔，已发出的模型/工具调用也不会因失去锁自动撤回。
锁获取发生 Redis 异常时有 fail-open 路径；因此不能声称所有故障条件下都严格单次执行。
本地模式可能使用内存状态/本地队列，可靠性必须与 Redis + QStash 部署区分。

相关实现：apps/server/src/services/agentRuntime/AgentRuntimeService/executeStep/{index,continuation,runSlotLease}.ts；apps/server/src/modules/AgentRuntime/{AgentStateManager,AgentRuntimeCoordinator}.ts。

4. 邮件 Inbox：最接近文章收件箱的路径

agent_inbox_messages 保存 sourceType/sourceId 指针、摘要、未读状态、线程与 topic 绑定、wakeClaimedAt。
sourceType/sourceId 唯一索引避免同一源记录重复入箱。内容保留在来源表。
AgentInboundService：验证/路由 provider 事件 → Signal → 记录 mail/inbox → 决定 skip/defer/wake → 限额 → claimWake → waker。
claimWake 原子更新未读且未占用/租约过期的行；默认租约十分钟。digest 用事务与 FOR UPDATE SKIP LOCKED 批量领取，合并一次处理。
waker 尝试沿邮件 threadKey 复用 topic，再调用 AiAgentService.execAgent；成功启动后标记已唤醒。
启动失败释放 claim，返回 503 让来源重试；启动成功与标记已读是不同步骤，需要考虑该边界上的故障。
外部正文以 untrusted_inbox 包装，并使用专门工具集。邮件触发 run 使用 headless；出站审计让外部来信 topic 的 send 进入必须干预路径，避免未经确认回复外部人。
最终结果通过完成 hook 投递 owner direct Channel，以 requestKey 去重；无事时允许保持安静。

相关实现：packages/database/src/{schemas/agentInboxMessage.ts,models/agentInbox.ts}；apps/server/src/services/agentIdentity/{inbound,waker,untrusted,ownerChannel}.ts；packages/builtin-tool-agent-account/src/outboundAudit.ts。

5. 群聊唤醒与“什么时候值得说话”

BotMessageRouter 按平台消息入口与会话策略接入；wakeDecision 结合显式提及、DM、规则、订阅、conversation 状态与 classifier 决定。
internalRules 排除自己、bot、系统、只有表情、提及别人等情况；ownerRules 处理频道范围、follow-up 窗口、沉默预算和 owner presence。
classifier 以结构化概率/消息类型判断是否对 agent 发问；duty 与 initiation 又有独立规则。
WakeScheduler 是纯状态机：idle → collecting → running → cooldown；调用者提供时间并执行 effects。
同一频道合批、冷却、run lease watchdog；pending 上限 20，超限丢弃最老项。
生产适配器用 Redis 状态和延迟队列做 flush；此 scheduler 在本地队列模式不启用。
仅调度 follow-up 唤醒；显式 @、reply、DM 和 command 有即时路径，不能将这个状态机的串行保证扩大到全部入口。
存储不可用时 submit 返回 unavailable，调用者可回到立即唤醒行为，是可用性与严格节流的取舍。

相关实现：apps/server/src/services/conversationWake/{classify,gate,policies/*,scheduler/machine,scheduler/service}.ts；apps/server/src/services/bot/wake/scheduler.ts；BotMessageRouter/wakeDecision.ts。

6. 定时任务与持续任务

Task 的长期业务状态、TaskTopic 的运行关联与 agent operation 分开保存。
heartbeat-tick 读取数据库，检查 archived、terminal、tickToken、模式、间隔、等待人工及已有运行。
schedule-dispatch 根据 cron/timezone 和 occurrence 找到应执行任务，CAS 预留 occurrence，再投递 QStash；明确投递失败可释放预留。
schedule-tick 再次核验当前模式、暂停、计划是否已修改、人工等待和次数上限。
TaskRunner 用条件状态更新争抢运行资格，组装任务 prompt、skills、模型和执行目标，调用 AiAgentService。
启动后事务登记 TaskTopic；若期间任务被删除/取消/撤回，尝试停止刚启动的孤立 operation，并报告停止是否得到确认。
完成路径推进长期任务生命周期，watchdog 收敛孤立 running topic、处理 interruption，并恢复结果回传。
LocalTaskScheduler 用内存 setTimeout；进程退出会丢失待触发定时器。QStash 模式的延迟消息由外部队列持有。

相关实现：services/taskRunner/{index,heartbeatTick,scheduleTick}.ts；services/taskScheduler/impls/{local,qstash}.ts；router-hono/workflows/task/handlers/{scheduleDispatch,watchdog}.ts；services/taskLifecycle/reconcile.ts。

7. 结果回传与“生成了结果”和“送达了结果”

TaskResultBridge 先以稳定 messageId 写回原 topic，PostgreSQL advisory transaction lock 避免并发写重复回传节点。
随后在 Redis 建 receipt，按来源 topic 合批唤醒创建者 agent，让它处理完成结果。
receipt 有 pending/processing、重试/超时和恢复索引；callback receipt TTL 为六小时，watchdog 会尝试恢复过期 processing。
向 bot 平台发送时记录已发送 chunk 计数，重试从未送达部分继续。
邮件 owner report、任务 callback、平台消息 callback 和浏览器本地 outbox 是不同机制；不能只根据文件名 outbox 判定统一的全局消息保证。
跨 PostgreSQL 与 Redis 的步骤没有一个共同事务，因此部署和补偿路径仍然重要。

相关实现：services/taskResultBridge/{index,redisStore}.ts；services/agentIdentity/ownerChannel.ts；services/bot/BotCallbackService.ts。

8. AgentSignal 与长期记忆

AgentSignal：source → signal/action → executor result → 后续 signal。共享包只定义语义类型和构建器，应用层安装策略与数据库/模型适配。
orchestrator 每次按 scenario 构建运行时、执行 policies、持久化 observability 与 receipts。
默认 assembled runtime 的 waypoint 后端为内存；存在 Redis adapter 文件不等于该主路径自动采用了它。
source ingress 有 Redis TTL 去重和短期 scope lock。源码先写 dedupe，再尝试 lock；锁只覆盖生成窗口，不覆盖后面的整个策略执行。
静态推断：若同 scope 的另一个事件取得 dedupe 后未取得 lock，并以相同事件标识重试，需检查调用方是否补偿；不能把 scope_locked 直接等同于已经可靠入队。这是待复现的故障场景，不是本次验证过的线上问题。
self-iteration scenario 安装 intent 分析、nightly review 与 completion policy，支持反馈进入记忆/skills/复盘等后续工作；实际启用受 feature gate 和策略约束。

独立 user-memory pipeline 使用 GateKeeper 判断哪些层值得提取，再并行运行 activity、identity、context、preference、experience 五层 extractor。
提取结果有结构化 schema、分层错误和记录；服务端负责上下文查询、持久化、embedding 与 workflow。
ContextEngine 按顺序运行 provider/processor，UserMemoryInjector 把已准备好的记忆渲染进入上下文；压缩、历史截断、记忆检索属于不同阶段。
长对话摘要、业务任务进度、用户长期记忆、团队 agent 技能不应被统称成同一个 memory。

相关实现：services/agentSignal/{emitter,orchestrator,sources/index,runtime/AgentSignalRuntime,runtime/AgentSignalScheduler}.ts；packages/memory-user-memory/src/{services/extractExecutor,extractors/gatekeeper,types}.ts；packages/context-engine/src/{pipeline,providers/UserMemoryInjector}.ts。

四、横向结论（以下是基于代码的判断）

1. Anthropic 给出架构检查维度；DeepSeek 展示单仓库授权工作如何持续推进；LobeHub 展示这些能力如何与多入口、多宿主和完整产品生命周期组合。
2. DeepSeek 最值得研究的是领域状态机、不可变授权、follow-up ownership、同步事务核心加持久副作用队列。
3. LobeHub 最值得研究的是宿主无关 runtime/executor/transport、上下文组装、可暂停工具调用，以及邮件/群聊/任务不同入口的具体恢复策略。
4. 设计 always-on 时，应分别说明 Event/Thread/Task/Run/Session/Memory/Permission/Delivery 的身份和持久化边界。
5. “恢复对话”只能说明 agent 能继续思考；外部写操作不重复、授权仍有效、结果能送达，必须分别设计与验证。
6. 静态阅读能确认分支、状态和检查存在；模型是否始终遵守范围、部署是否真正启用队列/调度、故障下副作用是否重复，需要运行验证。
