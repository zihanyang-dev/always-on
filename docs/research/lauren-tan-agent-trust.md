## 对本仓库的启发与判断

以下是结合 Always On 现状的判断，不是演讲原话，也不表示她推荐了我们的技术栈。

### 把需要反复提醒的知识放回模块

用户反复指出嵌套、转发和难读的执行顺序，说明现有实现仍要求读者记住太多细节。应该首先减少这些约束：Session 模块拥有接收事务，Run 模块拥有租约与最终提交，Pi/E2B 实现拥有各自协议和资源清理。接口需要让调用者少协调状态，不能仅把原来的复杂代码搬进辅助函数。

这也支持我们继续使用 Pi 的公开能力，让它维护模型和工具循环。本产品维护执行授权、持久状态及用户可见行为，避免复制 SDK 内部循环或围绕它构建一套庞大的替代框架。

### 清理会影响下一次生成

本轮删除没有产品调用者的通用 Inbox 写入入口，以及正式 Agent Worker 已经替代的诊断队列。相关测试中有价值的输入校验、来源隔离和 Redis 断连行为迁移到真实 Session/Run 链路验证。这样后续 Agent 搜索输入接收或 Worker 时，会找到当前使用的实现。

原有数据库迁移、仍然有效的 Better Auth 补丁和 SDK 必需的空钩子有明确职责，应保留。判断依据是调用关系和行为约束，不能把短小、暂未扩展或没有复杂实现等同于垃圾代码。

### 保留解释约束的注释，同时检查实现本身

我们遵循用户和代码规范的要求，保留英文注释，解释锁等待后的租约复查、工具执行前记录意图、未知结果不能重放、取消与成功的竞态，以及 SDK/沙箱收尾和队列退出的顺序。

每条这样的注释都需要对应实际实现和验证。注释不能成为吞错、关闭校验或保留旧路径的依据。也不通过要求每个函数都有注释来制造另一种噪声。

### 后端交付应提供可以检查的行为证据

对当前产品最重要的证据是：重复提交只生成一次 Run，旧 owner 无法继续写入，撤销权限后无法执行工具，浏览器断线不会取消执行，工具结果未知时不会盲目重跑。

本轮把断连回归放到真实 Agent Worker：只切断它自己的 Redis 连接，检查退出失败是否被报告、资源是否释放及 PG 中的取消结果。停止执行和队列 I/O 有不同生命周期，不能为缩短函数把两者混成同一个超时。

后续更复杂的恢复行为值得用状态图和状态转换测试表达。当前先把真实故障路径测清楚；只有具体问题需要时再引入模型检查或证明工具。

### 自动化规则需要明确适用范围

现有 Biome 承担可确定的语法约束：参数数量、嵌套三元、无用 else、默认导出、enum、namespace、参数属性、类型导出及 ts-ignore。环境变量读取限定于启动入口和测试；Web 源码限制 Node 运行时模块及 Agent 执行包依赖。

配置文件保留框架要求的默认导出；Node 限制只作用于浏览器源码。规则采用 Biome 官方实现，并用正反例核对。职责是否内聚、函数是否易读、注释是否准确继续人工审查，不用括号数量或注释密度的正则替代设计判断。

### 逐步增加自主性

先让一次开发稳定做到：理解现有入口、完成修改、删除废弃路径、运行相关验证、交付可审查证据。之后再考虑定时巡检、自动修复和合并。

产品内的长任务也应遵循同样顺序：工具有明确能力，结果可以验证，失败有持久记录，恢复有证据。增加 Router、更多 Agent 或更长循环，需要服务于已经明确的产品行为。
